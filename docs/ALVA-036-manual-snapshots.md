# ALVA-036 手动全局快照

## 行为与边界

只有业主显式点击“保存版本”才创建一个编号、数据库时间戳和完整项目状态组成的快照。没有已确认户型的问卷/候选工作稿同样可以保存；这类快照暂不能生成含房屋图的交付包，导出明确返回422。保存只校验已有正式场景，不重新分析、不修改已确认取舍，也不把未决问题改为已完成。

场景、二维候选、确认拓扑及其版本、对应建筑3D/候选/生成状态、回答、问卷草稿、原话、业务取舍、未决项、消息、资产及扩展偏好字段一起保存。正常编辑、确认、分析、生成只更新工作稿和必要业务依据，不新增全局存档。`changes`是既有的业务依据，不提供操作重放或撤销。

新快照投影排除历史`budget`字段、旧预算题Q19–Q22/Q60及专属原话依据；关联依据引用、分析游标和问卷游标保持一致。工作稿和既有快照不做破坏性迁移。其他问卷票的新范围由其自身维护，本票不修改现役问卷采集或专业授权。

本票不实施ALVA-037的列表/只读预览或ALVA-038的全局替换恢复；既有恢复入口不是这两票的完成证明。集成不等于部署，不自动重建生产`web/dist`或重启服务。

## HTTP与持久化合同

`POST /api/save`接收严格对象`{requestId, expectedRevision, confirmed:true}`；requestId为UUID，版本非负整数。身份和项目由服务器会话决定；未登录401、非业主403、无明确确认400、版本冲突409。

成功响应保持既有Project字段，增加`saveReceipt:{requestId,version,revision,createdAt}`。此回执引用本次请求最初成功提交的快照；重试响应中的Project始终是当前工作稿，可能比回执更新，客户端不得拿旧回执状态回滚当前工作稿。重复同一ID与相同内容不会新增快照；同ID不同内容409。

`AlvaStore.mutate`在同一事务中锁定项目、检查去重与版本、插入快照、更新当前工作稿、写入去重凭据。任一步失败整体回滚。故障日志独立记录，日志写入失败也不会掩盖原错误。新`alva_commands.response`仅保留`command-receipt-v1`、revision及保存时的savedVersion，不再每个操作存一份完整项目。旧完整响应凭据继续兼容，不删除历史行。

前端`SaveControls`同步阻止重复点击，清楚区分正在保存、结果未确认、已保存、版本冲突。会话存储只保留项目对应的请求ID/expectedRevision，绝不保存工作稿副本；网络响应丢失或刷新后继续复用同一请求。冲突必须显式重读，再由用户重新点击保存；重读本身不创建快照。响应超过30秒视为未确认，不能假定服务器未提交。

## 文件归属

服务端`api/snapshots/`负责保存路由和投影，事务由`api/store.ts`维护；无副作用合同在`packages/contracts/alva/snapshots.ts`；前端位于`web/src/snapshots/`，`main.tsx`仅装配页头保存控件。`api/export.ts`只增加无正式场景的明确错误。没有新增依赖或独立数据库。

## 可复跑验证

```sh
npm run check
node --import tsx --test --test-concurrency=1 tests/alva-snapshots.test.ts
npm run build:alva
node --import tsx scripts/alva-snapshots-check.ts
```

只用独立工作区、合成数据和空闲本地端口。重型任务按`.git/alva-heavy-task.lock`串行，使用任务级CPU/内存限制；不得连接生产数据库或冒充真实模型质量验收。

数据库验收覆盖保存后的全部字段比对、保留已知悉/专业待核实状态、保存INSERT后故障回滚、命令凭据INSERT后真实数据库故障回滚、重复并发请求、另一设备版本冲突、原请求重试与后续工作稿共存、预算投影、旧凭据兼容和关闭重开数据库。浏览器通过真实HTTP制造失败和冲突；“响应丢失”会先向真实服务发送并提交，再丢弃响应，而不是伪造成功数据。

实际结果、原实现提交与集成状态以本票Implementation handoff及对应独立evidence run为准；本文不把脚本存在等同于验收通过。
