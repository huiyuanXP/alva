# 后续功能任务 Prompt：主 Chat 接入

把以下段落放进每个获准实施的用户功能 Ticket 或执行 Prompt；变量按该票填写，不能只贴模板就宣称适配完成。

> 功能：`<功能名>`；用户意图示例：`<自然语言请求>`；权威业务模块/API：`<路径>`；确认条件：`<谁在何时确认>`；项目状态与候选：`<字段>`。
>
> 先读 `docs/ALVA-065-main-chat-agent.md`、`api/main-chat-agent.ts`、`api/chat.ts` 和 `api/codex.ts`。以登录后左侧咨询栏和 `POST /api/chat` 为主 Agent 入口，沿用现役 Codex App Server Harness。完成业务功能后，在**同一 Ticket** 中实现主 Chat 的受控工具适配；使用户能用上面的意图发起并看见进度/候选/结果。工具调用已有服务端业务逻辑，不复制数据库写入，不把直接按钮或模型口头说明当作 Agent 调用。
>
> 写清工具名称、用途、输入 schema、输出、权限、项目版本/幂等、失败与取消、是否需要用户确认。附件类输入写明如何从 Chat 安全传入实际附件；不能让模型根据文件名假装已读取。模型只能提出候选或请求确认；需要确认的行为由服务端核验，Chat 不可自行宣布已保存、采用或完成。若现役 Harness 无法安全表达这个调用，在本 Ticket 内做最小必要扩展并验证；不要临时开放 shell、文件写入或任意 HTTP 工具。
>
> 验收：从真实/隔离 Chat 输入自然语言，证明模型实际调用指定工具并返回可见结果；验证参数错误、越权、取消/重试及重读项目状态；保留独立 run 证据。同步功能文档、接入合同、交接和 NextTask。仅当端到端路径通过，才报告“主 Chat 已接入”；否则明确标为“业务功能已完成、Chat 适配未完成”，不能把整票写为完成。

对于已有功能补接，先列出直接 API/按钮与主 Chat 工具的差距，再按同一验收标准实施。不能把 Prompt 当作运行时自动注册机制；工具必须在 `api/chat.ts` 明确注册，并由服务端执行业务校验。
