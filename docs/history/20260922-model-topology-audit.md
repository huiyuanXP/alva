## 2. Gemini 3.8 实测

当前平台模型目录 GET `/v1/models` 返回 200，列出了 `gemini-3.8-flash-high`。这只是目录可见，不等于路由可用。

| 请求 | 实际结果 | 耗时 |
|---|---|---:|
| `/responses`，model=`gemini-3.8-flash` | HTTP 503，`model_not_found`，default 组没有可用渠道 | 0.145 秒 |
| 通过现有 Codex App Server，model=`gemini-3.8-flash-high`，要求调用一次合成只读工具 | 进程探针退出 1，上游报 `unknown provider for model gemini-3.8-flash`；工具闭环未通过 | 0.897 秒 |

因此没有把任何默认路由切到 3.8，也没有以“目录有名字”作为接入成功。平台需要先核实该别名实际映射的上游模型、provider与渠道能力。本机再换一个名称或盲目重试不能解决这一已返回的上游路由错误。

官方 Gemini 模型目录使用 `gemini-3.8-flash`；`-high` 是本平台暴露的别名，不能自动视为官方型号。官方文档可核对：`https://ai.google.dev/gemini-api/docs/models`。Codex 配置参考：`https://developers.openai.com/codex/config-reference/`。MiMo 官方已提供 Codex/Responses 配置说明：`https://mimo.mi.com/docs/zh-CN/tokenplan/integration/codex-configuration`；文档支持不等于当前主机已验证成功。

## 4. 拓扑校验与前端映射的确定性缺陷

本轮用当前真实校验函数执行离线合成反例，没有 mock 模型或改写生产数据：

| 反例 | 导入的 validateScene | 确认用的 validateTopology |
|---|---|---|
| T 形连接，长横墙放前面 | 通过 | 拒绝：竖墙端点落在横墙中段 |
| 完全相同的几何，只交换墙数组顺序 | 通过 | 通过 |
| 两墙直接交叉 | 通过 | 拒绝 |
| 短墙完全包含于长墙，短墙在前 | 通过 | 通过 |
| 同一包含关系，长墙在前 | 通过 | 拒绝 |
| 合成外边界存在 4cm 断口 | 通过 | 通过，未提示连接异常 |
| 两个房间多边形大面积重叠 | 通过 | 通过，未提示重叠 |

`api/topology/validate.ts:20–25` 只检测后一个墙的端点是否落在前一个墙中段，没有对称检测。因此结果依赖数组顺序。导入和确认也使用不同校验门槛，可能先报告导入成功，稍后校准或修改才失败。墙、房间边界和门窗邻接没有统一的拓扑图约束；不能用单个多边形不自交代替整屋拓扑正确。

两个历史候选亦未通过今天的严格检查：真实附件历史候选 16 墙/6 房间/14 开口，发现同墙门窗重叠；合成候选 7 墙/2 房间/4 开口，发现未分段 T 形连接。历史候选文件都经 JSON/schema 解析后保持墙坐标不变；这不是“JSON解析随机改错坐标”的证据。历史验收标准随代码更新过，不能把今天发现的缺口伪装成当时已运行过的检查。

前端还有独立显示问题：`web/src/main.tsx:18,22` 把原图拉伸到候选几何包围盒，使用 `preserveAspectRatio="none"`，没有固定像素→场景变换。原图宽高比为 1.639，历史真实候选为 1.859，若按现有逻辑叠图，相对横纵比约被改变 13.4%；这是显示映射的数学结果，不是现场尺寸误差。修改候选的最外边界还会改变底图映射，影响对照修正。
